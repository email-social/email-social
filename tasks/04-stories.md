# Task 4 — newsletters as stories

New pull request on `main` after Task 3b. The maintainer's idea (3 October): newsletters are not chats and not plain "Other mail" either. They belong in a strip at the top, like stories in messengers: one circle per sender, gone after a week, one tap to unsubscribe, images only when the reader asks for them. Transactional automated mail (order confirmations, password resets, delivery reports, bounces) is never a story. The protocol reserves a record type `es.social.story` so that a sender who uses Email Social can mark a promotion explicitly; such a message always has an ordinary `text/plain` form, like every other message.

Read `CLAUDE.md` first. Rule 2 matters most here: nothing leaves the client on its own. A story is read without any request to the sender; the only outgoing requests are the ones the reader taps.

## Deliverables

### es-core
A. **`storyOf(message)`** → `{ sender, title, receivedAt, expiresAt, unsubscribe, explicit } | null`, deterministic, built only from the parsed message:
   - A message is a story when it carries an accepted `es.social.story` record (`explicit: true`), **or** when all of these hold: `delivery.listUnsubscribe` is present; `List-Post` is absent (discussion lists are not stories); `autoSubmitted` is absent or `no`; `returnPath` is not `""` (bounces); the sender is not the account owner. `Precedence: bulk` on its own is not enough, and `Auto-Submitted: auto-generated` with an unsubscribe header is an automated message, not a story.
   - `title` = the subject without `Re:`/`Fwd:` prefixes, or the first line of the text when the subject is empty. `expiresAt` = `Date` + 7 days (a constant in one place), or `value.expiresAt` of an explicit record when earlier. `unsubscribe` = `{ oneClick: url } | { mailto: address } | { link: url } | null`, from `List-Unsubscribe` and `List-Unsubscribe-Post: List-Unsubscribe=One-Click` (RFC 8058) or from the record.
B. **The `es.social.story` record** in the lexicon next to `es.social.post`: `$type`, optional `author`, `value.via`, `value.createdAt`, `value.email.messageId`, `value.title` (≤ 200 UTF-8 bytes), optional `value.expiresAt` (RFC 3339 UTC), optional `value.unsubscribe` (`{ mailto }` or `{ url }`), `value.text` under the same 10000-byte rule as posts (`email.textSha256` otherwise). Written in that order. A story record MUST NOT carry `requestReceipts`, and a reader MUST NOT send any receipt for a story. `writeStory()` in the serializer, `readRecord()` accepts it; existing fixtures and vectors unchanged.
C. **Vectors** `packages/es-core/vectors/stories-*.json`: a newsletter with one-click unsubscribe; a newsletter with `mailto:` unsubscribe and `Precedence: bulk`; a discussion list (List-Id, List-Post, List-Unsubscribe) that is not a story; an order confirmation (`Auto-Submitted: auto-generated`, no unsubscribe) that is not a story; a password reset with an unsubscribe header that is not a story; a bounce; an explicit `es.social.story` message that round-trips through `writeStory` and `readRecord`; a story older than 7 days. Addresses from `example.com`, `example.org`, `example.net` only.

### es-bridge
D. `GET /api/stories`: the account's stories not yet expired, newest first, grouped by sender, each with `title`, `receivedAt`, `expiresAt`, `unsubscribe` kind, `messageId`, `seen`. Hidden senders left out. `seen` is the IMAP `\Seen` flag; opening a story sets it.
E. `POST /api/stories/unsubscribe` with `messageId`: for `oneClick`, one `POST` to that URL with the body `List-Unsubscribe=One-Click` and nothing else, no cookies, no redirects followed beyond one, 10-second timeout; for `mailto`, one message through the account's SMTP with the subject the header gives (or "unsubscribe") and an empty body; for `link`, no request, the client opens the URL in the browser. On success the sender goes on the account's hidden list and the response says what was done. This is the only request the bridge ever makes to an address outside the mailbox, and only on this call.
F. `POST /api/stories/hide` with `sender`: adds the sender to the hidden list (a JSON file next to the cache, mode 0600, per account); `DELETE` removes it. Hidden senders still appear under Other mail. The same per-account file becomes the home of the `receipts` setting from Task 3b (today given on the command line or in the login form), so that an account remembered in the keychain keeps it; the command-line and form inputs stay and write into the file.
G. Story content for the viewer: the message's HTML part reduced the way section 6.7 of the spec describes, plus a sanitized HTML form when an HTML part exists: scripts, styles, forms, iframes, objects and event handlers removed, every `src` and `srcset` moved to `data-src`/`data-srcset`, links kept with `rel="noreferrer noopener"` and `target="_blank"`. Use an existing sanitizer with a permissive licence if one is already a dependency; otherwise write the allow-list reducer in es-core with tests, no new dependency.

### es-web
H. **Stories strip** at the top of the chat list: circles with the sender's initials, a ring while unseen, newest first, one circle per sender; tapping opens the viewer; the strip disappears when there are no stories. Senders already visible as chats are not in the strip.
I. **Viewer**: the sanitized HTML inside an `<iframe sandbox>` (no `allow-scripts`, no `allow-same-origin`, no `allow-forms`) via `srcdoc`, with a `Content-Security-Policy` meta tag in the document that forbids all network (`default-src 'none'`, `img-src data:`) until the reader taps **Load images**; that tap rewrites `data-src` back to `src` and relaxes `img-src` to `https:` for that story only, after a one-line note that loading images tells the sender the message was opened. Text-only messages show the reduced text. Below the content: **Unsubscribe** (with the kind shown: one tap, by e-mail, or opens a page) behind a confirmation, and **Hide sender**. Left/right moves between stories, like messengers.
J. Other mail keeps every story, expired or hidden, read-only as today.
