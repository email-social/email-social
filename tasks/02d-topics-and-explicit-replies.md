# Task 2d — topics instead of subjects, quote cards only for deliberate replies

Starts from `main` after the Task 2 pull request (2, 2b, 2c) is merged; this is a new pull request. All earlier guarantees stay: nothing leaves the machine except IMAP/SMTP, no message text on disk, receipts only to ES senders, plain e-mail always works (CLAUDE.md rule 1).

The maintainer's second run with a real mailbox, after Task 2c, found two things:
1. The subject is still a mail concept. It should be an **optional topic**: a name the user can give a thread, invisible between two Email Social users unless one names it, and still a sensible Subject for a recipient who reads ordinary mail.
2. A quote card appears above **every** message the user sends, because `send()` always answers the latest message from the other side (`packages/es-bridge/src/session.ts`, the `fromOthers` pick) and `replyContextOf` draws a card whenever the answered message is held. Messengers show the card only when the sender deliberately answered a specific message. There is no way to do that today: the bubble menu has only "Open original".

The design was checked against how mail clients group messages. The facts this task relies on (cite them with their sources in the new `spec/DEVIATIONS.md` entries): Gmail and everything Exchange-backed (Outlook desktop, new Outlook, Outlook.com, Outlook mobile) group a conversation by the **normalized subject** and use References only as confirmation, so a changed subject forks the conversation and an identical subject can merge unrelated mail; Thunderbird groups by **References/In-Reply-To only** (subject threading off by default), so a changed subject changes nothing there; Apple Mail is undocumented and leans on the subject plus a literal "Re:"; Seznam.cz is undocumented. The one configuration that keeps a single conversation everywhere is a stable References chain **and** a byte-stable base subject (`Re: <base>` from the second message on). The one way to start a new conversation everywhere is a new root (no In-Reply-To, no References) **and** a different normalized subject; neither alone is reliable. Outlook's "Conversation Clean Up" deletes messages whose text is wholly contained in a later message of the conversation, so quoting the whole previous message under every chat message deletes the recipient's own history; only Gmail hides previously seen text, Thunderbird and classic Outlook render every quote inline.

## Two independent things

**A topic** is a thread inside a chat. Every chat has one implicit topic; the user may name more. Only an Email Social user *names* a topic; a fresh mail (no threading headers, no reply prefix) from any client starts an unnamed one. A topic is identified by the Message-ID of its root message, never by the subject text. A message never moves between topics once placed, and a subject change on a message from an ordinary client moves nothing.

**A deliberate reply** answers one specific message and is the only thing that produces a quote card. A message typed without choosing a target is a continuation of the topic the composer is bound to, and gets no card anywhere: not in our client, not in the recipient's.

## Deliverables

### es-core (separate commits with their own tests)

A. **Carrier subject.** `carrierSubject(sender, others)` with `Pick<EsAddress, "name" | "address">` values → `"Message from " + display name` (the address when the account has no name) when the chat has one other person; `"Message from " + sender + " to " + the others' display names (addresses when they have none), sorted by address, at most three and then "+N"` when it has more. Exchange groups a conversation by the normalized subject alone, so a subject naming only the sender would merge a 1:1 chat and a group chat with the same recipient into one conversation. It is the Subject of the first message Email Social sends into a chat whose topic has no name, written once and then inherited byte-identically; never derived from message text. Every message after a topic's root carries exactly `"Re: " + normalizeSubject(root.subject).base`, built from the **root**, so `Re: Odp: Re: AW:` stacks from other clients never propagate. When the root's base subject is empty (a chat started by a "(no subject)" mail), our message becomes the root of a new topic with the carrier subject instead of inheriting `Re: `. A consequence to keep, not to fix: in a chat the other Email Social user opened, their carrier subject is `Message from <their name>`, so our messages go out as `Re: Message from <their name>`; the subject is a carrier for the recipient's grouping, never a label anyone reads in our client, and byte-stability beats readability. Pin it with a test. The first line of the text is no longer used as a subject anywhere: delete `subjectFromText` from `packages/es-bridge/src/session.ts` (line 130, caller at line 834) and its test "derives a subject from the first line…" in `packages/es-bridge/test/session.test.ts` (deleted, not rewritten); `firstLine` itself stays for `lastLine`. `subjectKey` (threading/subject.ts) joins the public API, es-bridge compares labels with it.

B. **`topicsOf(messages)`** takes the `EsMessage`s of one chat **oldest first, as `groupByParticipants` orders them**, and assigns every message a topic root id, deterministically, in this order:
   1. the ES part's `email.topicRoot` when that id is in the chat;
   2. the topic of the message it answers (`In-Reply-To[0]`, else the newest `References` id that is in the chat);
   3. no parent in the chat, but a non-empty base subject equal (by `subjectKey`) to an existing topic's base → that topic (Outlook replies without threading headers, DEVIATIONS D8);
   4. no parent in the chat, and the message either carries any In-Reply-To/References, or has a reply prefix (`normalizeSubject(...).isReply`), or has an empty base subject → the topic of the **previous message of the chat** (a reply to something we do not hold, a gateway-tagged or renamed reply, a "(no subject)" mail); the chat's first message is its own root;
   5. otherwise (a fresh mail: no threading headers, no reply prefix, a new non-empty base) → the root of a new topic, whatever client wrote it.
   Messages with `Auto-Submitted` other than `no` are ignored by `topicsOf`, `subjectNoteOf` and `replyCardOf`; the bridge already keeps them out of chats (`classifyMessage` → "automated" → Other mail). Returns `{ topics: Topic[], of: Record<string, { rootId: string; topicStart: boolean }> }`: `topics` in the order the roots appear, each `Topic` = `{ rootId, label, base, kind, count }` where `label` = the `email.topicLabel` of the oldest message of the topic that carries one, else null; `base` = the root's base subject; `kind` = `"named"` when `label` is set, `"carrier"` when there is no label and the root either carries an ES part or has a base subject of the carrier form (`Message from …`), `"plain"` otherwise; `count` = messages in the topic. `of` is keyed by `EsMessage.id`; `topicStart` is true when the previous message of `messages` belongs to another topic (true for the first message). The result depends on nothing but `messages`.

C. **`unquotedLines(quoted)`**, **`collapse(text)`**, **`unquote(quoted)`**, all exported. `unquotedLines` → the quoted text with `>` prefixes removed (any depth, with the optional space and the U+FEFF iOS Mail puts first; same shape as the `QUOTE` pattern in `quotes.ts`), attribution lines and Outlook header blocks (the en/cs/de/fr forms `splitQuoted` recognises) and `-----Original Message-----` dropped, as an array of lines. `collapse` replaces every run of white space (`\s`, NBSP U+00A0, narrow NBSP U+202F) with one space and trims. `unquote(quoted)` = `collapse(unquotedLines(quoted).join(" "))`.

D. **`isInterleaved(message)`** → the flag `splitQuoted` already computes in `assignRoles` (`quotes.ts`, `interleaved`), as an exported predicate; `QuotedSplit` keeps its three fields so the public test vectors do not change.
   **`quotedFragmentOf(message, parent)`** → the fragment of the parent the sender singled out, or null. Let `s = unquotedLines(splitQuoted(message).quoted)`, `q = collapse(s.join(" "))`, and `p = collapse(` the lines of `splitQuoted(parent).fresh` that do not match the quote pattern `/^[ \t﻿]{0,3}>/` `)`. Non-null when **all** hold: `q` is non-empty; `q` is a strict substring of `p` (not equal); `s` has at most 3 non-empty lines; `q` is neither a prefix nor a suffix of `p`, unless the parent's fresh text has at most 3 non-empty lines; `parent.textSource !== "html"`; `!isInterleaved(message)`. Everything else is null: a default Gmail, Outlook or Apple Mail reply quoting the whole message, a tail-trimmed quote, a quote of the parent's own quotes. The result is `s` joined by one space, cut to 140 characters at a word boundary. A pure function of the two messages; it never looks at dates or at which message is newest. Takes `Pick<EsMessage, "text" | "es" | "textSource">` like `quoteForReply` does.

E. **`replyCardOf(message, lookup, { inChat, self })`** replaces `replyContextOf`. `inChat` is a `ReadonlySet<string>` of the `EsMessage.id`s of the chat being shown; `self` the account owner's canonical address(es). Returns `ReplyCard | null`, `ReplyCard = { messageId: string | null, from: string, excerpt: string, attachment: string | null, clickable: boolean }` (`from` = display name, else address, else ""; `messageId` null when the target is not held; `clickable` true only when the target is held **and** in `inChat`; `attachment` = the target's first attachment name when held, else from the carried data). Rules:
   - a message with an ES part that carries `email.replyTo` → **always** a card, from the carried data (`from` = `replyTo.from.name` else `.address`, `excerpt`, `attachment`), whether or not the target is held; only `clickable` depends on holding;
   - a message with an ES part without `email.replyTo` → **null**, whatever In-Reply-To says (no shipped client can express a target, so an unmarked ES message is a continuation);
   - the account owner's own message (`from` in `self`) without an ES part (its Sent copy in a chat without ES parts) → parent = `In-Reply-To[0]`, else the last `References` id; card iff `splitQuoted(message).quoted` is non-empty and the parent is held and in `inChat`; `excerpt` = `quotedFragmentOf(message, parent)` when non-null, else the first 140 characters of `unquote(splitQuoted(message).quoted)` at a word boundary. Email Social writes a quote only on a deliberate reply and a chat without ES parts keeps no other record of one (rule 2), so the quote **is** the record;
   - anyone else's message without an ES part → parent as above; card iff the parent is held, in `inChat`, and `quotedFragmentOf(message, parent)` is non-null; `excerpt` = that fragment, `from` = the parent's sender;
   - for messages without an ES part: a parent outside `inChat` or not held → null.
   The old rules "parent card whenever held" and "subject card when the parent is not held" go away, with their tests (see the acceptance test). The `ReplyContext` type goes away; es-bridge's `ReplyCardView` = `ReplyCard` + `fromMe: boolean` (the target is the owner's own message), replacing `ReplyContextView`; es-web keeps rendering "You" for `fromMe`.

F. **`subjectNoteOf(message, topic)`** → the base subject, or null. Non-null only for a message **without** an ES part whose non-empty base subject differs (by `subjectKey`) from its topic's base: a gateway tag such as `… [EXTERNAL]`, a renamed reply. Shown as one small line on that bubble; it changes nothing else. Null for a topic root (its base *is* the topic's base).

G. **ES part fields**, all under `value.email` (the sub-object that is ours; the lexicon's `reply` stays unwritten and ignored, D10 unchanged):
   - `topicRoot`: Message-ID of the topic root; on a message that is itself the root, its own Message-ID; written whenever the root has one, left out when the root's `EsMessage.id` is a synthetic `sha256:` id (such an id cannot be written as a msg-id, `serialize.ts` `checkParentId`); a reader without `topicRoot` falls through to `topicsOf` rules 2–5;
   - `topicLabel`: string, written on **every** message Email Social sends inside a named topic (not only on the root, so the label survives the root falling outside the loaded window);
   - `replyTo: { messageId: string | null, from: { name, address }, excerpt }` only on a deliberate reply; excerpt = the first 140 characters of the target's fresh text at a word boundary; `messageId` null when the target has no Message-ID. TypeScript type `EsReplyToCard`; say in the schema comment that it has nothing to do with the RFC 5322 `Reply-To` header (`EsMessage.replyTo`).
   `EsOutgoing.es` gains `topicRoot?: string | "self"`, `topicLabel?: string`, `replyTo?: EsReplyToCard`; `serializeMessage` copies them into `value.email` and writes `options.messageId` for `"self"`. `esPartToWire` writes `email`'s keys in this order, after the existing ones, so output stays byte-stable: `messageId, subject, inReplyTo, references, textSha256, topicRoot, topicLabel, replyTo`, and inside `replyTo`: `messageId, from (name, address), excerpt`. `readEmailMeta` reads them liberally: a non-string `topicRoot`/`topicLabel` is dropped, a `replyTo` without a usable `from.address` is dropped as a whole, `messageId` through `normalizeMessageId`, `from.address` through `canonicalAddress`. Readers ignore unknown fields already; update the schema comment at the top of `es/schema.ts`, the vectors and `vectors/README.md`. `includeEsPart` semantics unchanged.

H. **Serialization.** `serializeMessage` takes `subject` and `inReplyTo` together for every reply (it already can); `References` as today. `quoteForReply` keeps its 40-line default; the bridge passes 5; the `[...]` marker stays.

### es-bridge

I. **`SendRequest`** loses `subject` and gains `replyTo?: string` (a `MessageView.id` of this chat: a Message-ID, or the `sha256:…` id of a message that has none) and `topic?: { root: string } | { label: string }`. Shape checks in `bridge.ts` (`/api/messages`): drop the `subject` check and passthrough (lines 400 and 406); 400 for a `replyTo` that is not a string, a `topic` that is not an object, a `topic` with both keys or neither, `topic.root` together with `to`, `replyTo` together with `topic`, a `label` that is empty after `collapse` or longer than 200 characters. Chat-relative checks stay in `send()` as `RangeError` (bridge.ts:427 turns it into 400): `replyTo` must be a message of this chat, `topic.root` a topic root of this chat. A new chat (`to`) takes an optional `{ label }` only.

J. **`send()`:**
   - the bound topic = the target's topic when `replyTo` is given (a deliberate reply continues the thread its target is in, as any mail client would; the UI shows the rebinding, K); else `topic.root`; else, for `topic.label`, the existing topic — named **or** plain — whose `subjectKey(base)` equals `subjectKey(normalizeSubject(collapse(label)).base)` (it **re-enters** that topic: no second root with a subject the recipient's client would merge anyway), else a **new root** (no In-Reply-To, no References, Subject = the collapsed label, `topicRoot: "self"`, `topicLabel`); else, when the request names no topic, the topic of the owner's own newest message in the chat, else the chat's newest topic;
   - a continuation answers the **newest message of the bound topic that has a Message-ID** (walk back; if none has one, send with the subject alone and no `topicRoot`); Subject = `Re: <root base>`; `topicRoot` = the root's id, `topicLabel` when the topic has one; no quote;
   - a deliberate reply answers its target (In-Reply-To, References from it; when the target has no Message-ID, the continuation's headers instead) with the same Subject rule; `email.replyTo` carries the card data;
   - quoting: to a chat where **no** recipient has ever sent an ES part, a deliberate reply ends with `quoteForReply(target, { maxLines: 5 })`; a continuation carries no quote; a message that carries an ES part never carries a quote (an ES post's text is exactly what the author typed; the plain members of a mixed chat get the deliberate reply without a quote, and no footer: write this down as a deviation);
   - footer: every message to a chat where no recipient has ever sent an ES part ends with the sentence `Sent with Email Social. Reply as you normally would; this is an ordinary e-mail.` After a `\n\n-- \n` delimiter when the typed text has no `-- ` line of its own; when it has one, as the last line of the user's own signature block, so a message never carries two `-- ` lines (RFC 3676 §4.3). Body order: text, blank line, quote (deliberate replies only), blank line, signature block. Because RFC 2045 §6.7 rule 3 forbids trailing white space in a 7-bit body, the `-- ` line makes such messages quoted-printable (`fitsSevenBit`, es-core/src/serialize.ts:258); the body still decodes to exactly the text, and the Sent copy read back has `-- ` unchanged and the footer under `signature`. Update D17 accordingly;
   - `MessageView` gains `topic: { rootId, label, kind } | null`, `topicStart`, `replyCard` (replaces `replyContext`), `subjectNote`, `interleaved`; all null/false for messages shown outside a chat (`OtherView.messages`, the contact page) and for `Auto-Submitted` messages. `ChatView` gains `topics` (with counts) and `composerTopic` (the default binding above; recomputed when a chat is opened). `views()` prefetches the texts of the parents of every message whose `quoted` is non-empty, so plain cards do not flicker in after the first render. Update the doc comments of `MessageView.subject` (`api-types.ts`) and `ChatEntry.subject` (`chats.ts`): the base subject, no longer "for the separator".

### es-web

K. **No "Subject" anywhere.** The new-chat composer and the open-chat composer share one control beside the text box. In a new chat and in a chat with a single topic it is a `+ Topic` chip that expands to a short input ("Topic — a name for this thread; leave empty for the ongoing chat"). In a chat with more than one topic the chip **always names the bound topic**: its label, else its base subject, else "Ongoing chat" for the carrier topic; tapping it offers the chat's topics and "New topic…". The binding is sticky while the chat is open and follows what the user last sent or chose (and the target of a pending reply, L); it is never recomputed from an incoming message.

L. **Reply.** The bubble menu (⋯) gains "Reply"; choosing it shows a chip above the composer ("Replying to Alice — excerpt", ✕ cancels) and rebinds the composer to that bubble's topic. Sending with it set passes `replyTo`.

M. **Timeline.** A quote card appears only where `replyCard` is non-null. A topic chip appears on a bubble with `topicStart` only when the chat has more than one topic, showing the label, else the base subject, else "Ongoing chat"; a chat with a single topic shows no chip at all; while the timeline is filtered to one topic no run chips are shown (the header names it). `subjectNote` renders as one small muted line. An `interleaved` message is rendered line by line: a line matching `/^[ \t﻿]{0,3}>/` gets `class="quoted-line"` (muted, the `>` not shown), every other line plain, under a one-line note "answered point by point"; no other bubble ever renders a quoted line. The "Show signature" control is not shown on the owner's own messages when the signature is, or ends with, the Email Social footer. The chat header gets "All topics ▾" listing the topics with counts, filtering the timeline and binding the composer. No separator lines; no quoted text under any other bubble; "Open original" stays.
